# 健康档案多成员管理与首页健康宣教优化 — 实施方案

## 一、概述（Summary）

对用户端小程序（`miniprogram/`）的「我的健康」进行档案管理细分优化，支持同一账号管理最多 5 个健康档案（本人/父母/其他亲属），每个档案可分别建档、自助评估、查看各自的评估记录；同时把「健康宣教」从「我的健康」页移除，改为在店铺首页展示一个「轮播图高度」的横向滚动板块。

后端在阶段五（8.2/8.3）已具备大部分能力（多档案 CRUD、relation 字段、评估 record_id 写入回写、宣教分类/文章），本次主要补齐 **两处后端缺口**（档案数量上限、评估列表按档案过滤）并完成 **C 端小程序前端改造**。

## 三、后端改动（3 处）

### 1. `server/internal/utils/constants.go`


### 2. `server/internal/handlers/health/record.go` → `UserCreateHealthRecord`
在 `ShouldBindJSON` 之后、`Create` 之前加入数量校验（超过 5 个拒绝）：

```go
var count int64
database.DB.Model(&models.HealthRecord{}).Where("user_id = ?", userID).Count(&count)
if count >= int64(utils.MaxHealthRecordsPerUser) {
    response.Fail(c, http.StatusBadRequest, response.CodeParamError, "最多可创建 5 个健康档案")
    return
}
```

> 说明：`UserUpsertHealthRecord`（旧单档案兼容接口）只会在「无档案时新建 1 条、有则覆盖最新一条」，不会触发超限，故不改动。

### 3. `server/internal/handlers/health/assessment.go` → `UserListAssessments`
支持 `record_id` 查询参数过滤（不传则返回全部，兼容旧行为）：

```go
var total int64
```

- `goEditRecord()` 改为 `/pages/store/health-record-edit?id=${activeId.value}`（有成员时）或 `/pages/store/health-record-edit`（无成员时新建）。

## 五、假设与决策（Assumptions & Decisions）

1. **「最多 5 个」由后端强制**，前端仅做 UI 上的「添加成员」按钮隐藏（`records.length >= 5` 不显示），双保险。
2. **评估记录按档案隔离**：`查看评估记录` 与 `自助评估` 都绑定「当前选中成员」的 `record_id`；未选成员时 `record_id` 不传，走后端「最近档案/全部」兜底。
3. **删除成员**：长按成员卡片触发删除确认；被服务订单引用的档案由后端拒绝并透出提示（`recordReferencedByOrders` 已有）。
4. **健康宣教首页板块**：复用 C 端公开接口 `/store/education/articles`（`OptionalJWTAuth`），未登录用户也可浏览文章列表；进入详情/更多仍走既有登录流程（`education-detail` / `health-education` 页面行为不变）。
5. 不改动路由（遵守「路由文件不可在中间件重构时修改」之外的既有约定 `main.go` 本次也无需新增路由，仅复用现有接口与常量）。
6. 不新增数据库迁移：`relation` / `record_id` 列均已存在于 011/演进中；数量上限为代码层校验。
