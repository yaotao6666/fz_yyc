# master 分支商品列表上拉加载修复计划

## Summary
- 目标分两段执行：
  1. 先把当前 `master` 工作区里的未提交改动安全迁移到新建本地 `dev` 分支，并在 `dev` 上提交保存；
  2. 再回到干净的 `master` 分支，修复 `pages/merchant/products/list` 无法上拉加载的问题。
- 本次优先采用最小改动方案：不动数据库、不新增接口，优先修正商品列表页的滚动容器和分页判断，并在必要时补齐前端 API/类型的分页口径。

## Current State Analysis

### Git 状态
- 当前仓库所在分支是 `master`。
- 本地不存在 `dev` 分支。
- 当前可见分支只有：
  - 本地：`master`
  - 远端：`origin/master`
  - 远端：`origin/trae/solo-agent-000XbQ`
- 当前工作区存在大量未提交改动和未跟踪文件，覆盖：
  - `miniprogram/`
  - `server/`
  - `docs/prd/`
  - `.trae/specs/`
- 这些改动如果直接在 `master` 上切换、修 bug，容易与本次修复混在一起，不利于回退和验收。

### 用户已确认的分支策略
- `dev` 的准备方式：新建本地 `dev`
- 当前未提交改动的保存方式：提交到 `dev`

### Bug 现状
- 目标页面：`miniprogram/src/pages/merchant/products/list.vue`
- 当前页面使用：
  - `scroll-view` + `scroll-y`
  - `@scrolltolower="loadMore"`
  - `page/page_size/noMore/loading` 做本地分页控制
- 当前实现存在两个实际风险点：
  1. `scroll-view.product-list` 没有明确可滚动高度，仅设置了宽度和内边距，同时页面底部还有 `position: fixed` 的 `.bottom-bar`，容易导致触底事件不稳定；
  2. `loadProducts()` 的“是否还有下一页”只靠 `res.list.length < pageSize` 判断，没有使用后端真实返回的 `pagination.total/page/page_size`。

### 接口口径现状
- 后端商家商品列表接口：`server/internal/handlers/merchant/product.go` 的 `GetProducts()`
- 后端返回结构是：
  - `list`
  - `pagination.total`
  - `pagination.page`
  - `pagination.page_size`
- 前端 API：`miniprogram/src/api/index.ts` 的 `getProducts()`
  - 当前只把 `list` 做了 `normalizeProduct`
  - 没有像其它列表接口一样走 `normalizeListField`
- 前端类型：`miniprogram/src/types/index.ts` 的 `ProductListResponse`
  - 当前声明为顶层 `total/page/page_size`
  - 与后端真实返回的 `pagination` 对象不一致

## Proposed Changes

### 一、分支切换与未提交改动安置

#### 1. 新建本地 `dev` 分支
- 在当前 `master` 基础上新建本地 `dev`
- 目的：
  - 给当前大批未提交工作一个稳定落点
  - 避免本次 bug 修复继续叠加在脏的 `master` 工作区上

#### 2. 在 `dev` 上提交当前未保存改动
- 将当前所有需要保留的未提交改动在 `dev` 上整理并提交
- 提交范围按当前工作区状态收口，不回退用户已有改动
- 目的：
  - 为后续切回 `master` 提供干净工作区
  - 保证现阶段工作成果不会因切分支丢失

#### 3. 切回 `master`
- 确认 `dev` 已保存后，再切回 `master`
- 若 `master` 仍提示工作区不干净，则先检查是否存在未被纳入 `dev` 的残留文件，再决定是否补提交或清理

### 二、`pages/merchant/products/list` 上拉加载修复

#### 4. 修正滚动容器的可滚动高度
- 文件：`miniprogram/src/pages/merchant/products/list.vue`
- 计划修改：
  - 将页面根容器改为稳定的纵向布局容器
  - 给商品列表滚动区域明确可计算高度或使用 `flex: 1` + 受控容器高度
  - 为底部固定操作栏预留足够底部内边距，避免最后一屏内容被遮挡
  - 必要时补 `lower-threshold`，降低触底触发门槛
- 目的：
  - 让 `scrolltolower` 在真机和开发工具里都能稳定触发

#### 5. 收紧分页状态控制
- 文件：`miniprogram/src/pages/merchant/products/list.vue`
- 计划修改：
  - 保留 `loading` 防重入
  - 增加基于服务端分页信息的 `hasMore/noMore` 判断
  - 在筛选、搜索、分类切换时统一重置 `page/products/noMore/loadingMore`
  - 防止重复触发 `loadMore()` 时连续请求同一页
- 目的：
  - 即使滚动事件触发正常，也避免因为本地分页状态判断不准导致“看起来不能继续加载”

#### 6. 对齐商品列表接口返回结构
- 文件：`miniprogram/src/api/index.ts`
- 计划修改：
  - 让 `getProducts()` 和其它列表接口保持一致，统一归一化 `list` 与 `pagination`
- 文件：`miniprogram/src/types/index.ts`
- 计划修改：
  - 修正 `ProductListResponse`，改为与后端一致的分页结构
- 目的：
  - 让页面可以直接依据后端分页信息做是否继续加载的判断
  - 消除当前前后端类型口径不一致问题

#### 7. 只在必要时调整后端
- 文件候选：`server/internal/handlers/merchant/product.go`
- 默认策略：
  - 先不改后端
- 只有在实际验证发现 `pagination` 字段不稳定、页码异常、返回数量异常时，才补最小后端修正
- 目的：
  - 控制变更范围，优先把 bug 收敛在前端分页和滚动容器

## Assumptions & Decisions
- 假设 `pages/merchant/products/list.vue` 在 `master` 分支上的主体结构与当前读取结果接近；如果切回 `master` 后代码不同，以 `master` 实际文件为准微调实现。
- 决策：本次不采用 `stash` 迁移未提交改动，统一在新建 `dev` 上提交保存。
- 决策：本次 bug 修复优先做“滚动容器 + 分页口径”双修，不扩大到商品列表页面重构。
- 决策：不回退当前工作区里用户已有改动；若分支切换时遇到冲突，以保留现有改动为第一原则。
- 决策：若 `master` 切换后复现发现根因只在样式高度，则 API/类型改动仍保留为建议项；若已证明确实依赖后端分页信息，则一并纳入修复。
