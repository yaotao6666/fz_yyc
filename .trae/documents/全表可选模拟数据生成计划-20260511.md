# 全表可选模拟数据生成计划

## Summary

目标：为当前项目补充一套“可选导入”的中等规模模拟数据，保证 `server/migrations/20240101000000_full_init.sql` 创建出的全部业务表都能获得数量合理、关系完整、可支撑页面联调与统计看板的数据，同时保留现有“最小初始化”默认口径不变。<mccoremem id="03g3w0g2dmbrqa2sf2l6pq3nw" />

本次计划不直接把完整模拟数据塞进默认初始化 SQL，而是采用：

1. 保留 `20240101000000_full_init.sql` 作为最小初始化入口
2. 新增一份可选的完整 mock seed SQL
3. 补充脚本、验证工具与文档，使开发者可以按需导入完整模拟数据

## Current State Analysis

### 1. 当前初始化入口只有最小数据

已确认当前仓库唯一初始化入口为：

- `server/migrations/20240101000000_full_init.sql`

配套执行入口为：

- `server/scripts/regression-test.sh`
- `server/migrations/MIGRATION_GUIDE.md`

当前脚本尾部仅写入了以下最小数据：

1. 1 条服务商记录
2. 1 个服务商管理员账号：`admin / admin123`
3. 1 条商家记录
4. 1 个商家员工账号：`merchant / merchant123`
5. 1 条配送设置
6. 1 条营业执照

结论：当前仅能保证登录和最小联调，无法支撑列表、分页、统计和复杂业务链路。

### 2. 绝大多数表当前为空

1. `merchant_applications`
2. `categories`
3. `products`
4. `product_specs`
5. `users`
6. `user_addresses`
7. `user_visits`
8. `user_behavior_events`

17. `merchant_fees`
18. `merchant_rates`
19. `coupons`

21. `cloud_printers`

结论：用户提出的“保证所有表都有一定量合理的数据”本质上是一次覆盖全业务链路的种子数据建设，而不是补几张核心表。

### 3. 业务页面和接口确实依赖这些表

已确认多个核心接口依赖上述空表：

1. 商家数据分析接口依赖：
   - `orders`
   - `order_items`
   - `user_behavior_events`
   - `products`
2. 商家库存预警依赖：
   - `products`
3. 商家邀请统计依赖：
   - `invite_records`
   - `invite_rewards`
4. 商家打印机与打印日志依赖：
   - `cloud_printers`
   - `print_logs`
5. 服务商看板、商家排行、审核记录依赖：
   - `orders`
   - `merchant_audit_records`
   - `merchant_fees`
   - `merchant_rates`
   - `merchant_applications`
6. 公告与活动相关页面依赖：
   - `announcements`
   - `activities`

结论：如果只做“表非空”，但不构造正确关联关系，许多页面仍会显示异常或统计失真。

### 4. 当前文档口径与本轮目标冲突

已确认以下文档都还在强调“最小初始化数据”：

1. `server/migrations/MIGRATION_GUIDE.md`
2. `测试账号文档.md`
3. `server/migrations/REGRESSION_TEST_REPORT.md`

其中 `测试账号文档.md` 还明确写着：

- 不再预置 C 端用户、订单、商品和行为演示数据

结论：本轮即使采用“可选 mock 数据”方案，也必须同步更新文档，明确默认初始化和可选模拟数据是两种模式。

## Proposed Changes

### 1. 新增可选 mock seed SQL

文件：

- `server/migrations/20260511xxxxxx_mock_seed.sql` 或同级等价命名的新 SQL 文件

改动目标：

1. 在不破坏默认最小初始化的前提下，提供一份独立可导入的完整模拟数据 SQL
2. 覆盖 `20240101000000_full_init.sql` 已创建的全部业务表
3. 让数据关系满足真实页面与接口的查询方式

计划内容：

1. 按实体分层生成数据
   - 平台层：`service_providers`、`service_provider_admins`
   - 商家层：`merchants`、`merchant_applications`、`merchant_licenses`、`merchant_delivery_settings`、`merchant_staffs`
   - 商品层：`categories`、`products`、`product_specs`
   - C 端层：`users`、`user_addresses`、`user_visits`、`user_behavior_events`
   - 交易层：`orders`、`order_items`、`refunds`
   - 运营层：`invite_records`、`activities`、`invite_rewards`、`announcements`、`coupons`、`coupon_records`
   - 服务商配置层：`merchant_audit_records`、`merchant_fees`、`merchant_rates`
   - 设备层：`cloud_printers`、`print_logs`
2. 采用中等规模数据量级 <mccoremem id="03g3w0g2dmbrqa2sf2l6pq3nw" />
   - 商家：约 8-15 家
   - 每商家分类：3-6 个
   - 每商家商品：8-20 个
   - C 端用户：20-50 个
   - 订单：80-200 条
   - 行为事件：数百条
   - 其他日志/配置表：每表至少数条，能支撑列表与详情
3. 保证状态分布合理
   - 商家包含待审核、已通过、已拒绝、停用等状态
   - 订单包含待支付、已支付、已完成、已取消、退款中/已退款等状态
   - 邀请记录包含待完成与已完成
   - 公告、活动、优惠券包含启用与停用
   - 打印机包含默认/非默认、启用/停用
4. 保证时间分布合理
   - 近 7 天、近 30 天、近 12 个月均有数据
   - 当日数据足以支撑“今日/本周/本月/本年”看板
5. 保证金额和销量逻辑自洽
   - `orders.pay_amount` 与 `order_items.subtotal` 合理对应
   - `products.sales`、`merchants.sales_count` 与订单聚合量尽量一致
   - 低库存商品数量足以触发库存预警

改动原因：

1. 独立 seed 文件能兼顾当前“最小初始化”与“完整联调数据”两种需求
2. 单独文件更容易维护，不会让基础初始化 SQL 过度膨胀

### 2. 扩展初始化/回归脚本入口

文件：

- `server/scripts/regression-test.sh`

改动目标：

1. 为 mock 数据提供标准导入入口
2. 降低开发者手工拼命令的成本

计划内容：

1. 在现有 `init/reset/status/test` 之外增加 mock 数据相关命令，例如：
   - `mock`
   - `init-mock`
   - 或 `init --with-mock` 风格的等价实现
2. 执行顺序明确为：
   - 先导入 `20240101000000_full_init.sql`
   - 再导入新 mock seed SQL
3. `status` 输出可补充更多关键表计数，至少覆盖：
   - 商家
   - 商品
   - 用户
   - 订单
   - 邀请记录
   - 公告
   - 打印机

改动原因：

1. 当前脚本只支持最小初始化
2. 有标准命令入口后，mock 数据才能成为稳定可复用的开发环境能力

### 3. 扩展验证工具，避免“表非空但关系坏掉”

文件：

- `server/cmd/verify_seed/main.go`

改动目标：

1. 从当前只校验少数账号和少数表计数，扩展为校验 mock 数据完整性
2. 将“结构存在”升级为“关键表非空 + 关键关系成立”

计划内容：

1. 保留现有账号密码校验
2. 新增关键表计数校验
3. 新增关键关联校验，例如：
   - 每个模拟商家至少有配送设置和营业执照
   - 至少部分商家有分类、商品、规格
   - 至少部分用户有地址、访问、行为事件
   - 至少部分订单有订单项，至少部分订单有关联退款
   - 至少存在公告、活动、优惠券、打印机、打印日志、邀请记录、审核记录
4. 输出按模块分组的统计结果，便于快速发现哪类数据缺失

改动原因：

1. 本轮目标是“所有表都有合理数据”，需要工具化验证
2. 仅靠手工打开页面检查成本太高

### 4. 更新初始化与测试文档

文件：

- `server/migrations/MIGRATION_GUIDE.md`
- `测试账号文档.md`
- `server/migrations/REGRESSION_TEST_REPORT.md`

改动目标：

1. 明确区分“默认最小初始化”和“可选完整 mock 数据”
2. 让团队成员知道如何导入、验证、清理 mock 数据

计划内容：

1. `MIGRATION_GUIDE.md`
   - 增加 mock seed 文件说明
   - 增加新命令或导入方式说明
   - 说明两种模式的适用场景
2. `测试账号文档.md`
   - 从“当前不预置商品/订单/C端用户”改为：
     - 默认初始化不预置
     - mock 模式可选预置
   - 增加 mock 数据覆盖范围与使用建议
3. `REGRESSION_TEST_REPORT.md`
   - 更新测试前提，区分最小模式与 mock 模式
   - 补充 mock 模式下的关键表期望

改动原因：

1. 当前文档和本轮方案口径冲突
2. 文档不更新会导致后续误解“为什么 reset 后数据变了/没变”

### 5. 维持兼容的实现边界

明确本轮不做的事情：

1. 不修改表结构
2. 不变更现有账号口令
3. 不新增业务接口
4. 不把 mock 数据强行写入生产或默认部署流程

原因：

1. 用户当前目标是补全开发测试数据
2. 采用“可选导入”方案能把影响范围控制在开发/测试环境

## Assumptions & Decisions

1. 已确认采用“保留最小初始化 + 新增可选 mock 数据”的接入方式。<mccoremem id="03g3w0g2dmbrqa2sf2l6pq3nw" />
2. 已确认模拟数据规模采用中等规模，重点覆盖页面联调、分页和统计场景。<mccoremem id="03g3w0g2dmbrqa2sf2l6pq3nw" />
3. 决定不直接扩写 `20240101000000_full_init.sql` 的默认数据部分，而是新增独立 mock seed 文件。
4. 决定同步更新脚本、验证工具和文档，否则 mock 数据无法形成稳定使用方式。
5. 决定优先保证“关键关系正确”和“页面统计可读”，而不是追求超大规模压测数据。

## Verification Steps

执行后按以下步骤验证：

1. 最小初始化验证
   - 仅导入 `20240101000000_full_init.sql`
   - 确认仍只得到最小登录数据，兼容当前默认流程
2. mock 数据导入验证
   - 执行新增 mock 导入命令或二次导入 mock seed SQL
   - 确认全部业务表至少存在非零记录
3. 关键关系验证
   - 抽查商家是否拥有申请、执照、配送、员工、商品、打印机等关联数据
   - 抽查用户是否拥有地址、访问、行为事件、订单、优惠券记录等关联数据
4. 接口联调验证
   - 服务商看板、商家审核、商家列表、商家分析接口返回非空且分布合理
   - 商家端数据分析、商品排行、库存预警、订单列表、邀请统计、公告列表返回可用数据
5. 工具验证
   - `regression-test.sh` 新 mock 流程可成功执行
   - `verify_seed` 能输出关键表计数与通过结果
6. 文档验证
   - 文档中不再混淆“最小初始化”与“可选 mock 数据”两种模式
