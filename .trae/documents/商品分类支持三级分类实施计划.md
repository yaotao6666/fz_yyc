# 商品分类支持三级分类实施计划

## 1. 摘要
将当前「扁平单级」的商品分类升级为「最多三级」的树形分类：
- 数据库 `categories` 表新增 `parent_id`（自引用父级）与 `level`（层级，1=一级 2=二级 3=三级）字段。
- 后端分类 CRUD / 排序支持父级与层级校验（不允许超过三级、不允许删有子级的分类）。
- 管理端（web-admin）分类管理改为树形表格，商品分类选择改为级联选择器（三级）。
- C端 store 首页保持现有「左分类 + 右商品」平铺布局，不重构三级导航；商品可挂任意层，C端按分类查询时后端递归聚合「该分类及其所有子孙分类」的商品。

## 2. 现状分析

## 3. 变更内容

### 3.1 数据库迁移（新增迁移文件）
**新文件** `server/migrations/<timestamp>_category_hierarchy.sql`：
- `ALTER TABLE categories ADD COLUMN parent_id BIGINT UNSIGNED NULL COMMENT '父分类ID(0/空=一级)' AFTER name;`
- `ALTER TABLE categories ADD COLUMN level TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '层级: 1=一级 2=二级 3=三级' AFTER parent_id;`
- 存量数据回归：`UPDATE categories SET parent_id=NULL, level=1;`（保持所有现有分类为一级，不破坏现状）。
- `CREATE INDEX idx_categories_parent ON categories (parent_id);`
- 用与现有迁移一致的 `IF NOT EXISTS(查询 information_schema)` 防御式写法（参考 [20260814000001_cxsm_clean_and_expand.sql](file:///Users/yaotao/Documents/trae_projects/fz_yyc_cxsm/server/migrations/20260814000001_cxsm_clean_and_expand.sql)）。

> 不新增 `category_type` 相关分支：三级分类对「商品分类(1)」与「服务分类(2)」一视同仁，父级由用户选择，不做类型强制。

### 3.3 后端分类 handler 改造
**文件** [server/internal/handlers/merchant/product.go](file:///Users/yaotao/Documents/trae_projects/fz_yyc_cxsm/server/internal/handlers/merchant/product.go#L220-L361)：

1. `CategoryRequest` 增加可选字段 `ParentID *uint64 \`json:"parent_id"\``。
2. 新增私有辅助：
   - `loadCategory(db, id) (*models.Category, error)`：按 id 查分类。
   - `validateParentLevel(db, parentID *uint64) (level uint8, err error)`：`parentID` 为空返回 1；否则校验父分类存在、计算 `level = parent.level + 1`，若 `level > 3` 返回错误"最多支持三级分类"。
   - `countDirectChildren(db, id) (int64, error)`：统计 `parent_id = id` 的分类数量。
   - `collectCategorySubtree(db, rootID uint64) ([]uint64, error)`：按 `parent_id` 逐层收集 rootID 及其直接子、孙 ids（最多两层下钻），返回平铺 id 集合；用于商品聚合查询。
3. `GetCategories`：
   - 保持兼容：不带额外参数的返回改为「树结构」——只返回 `level=1` 的根节点，每个节点带 `children`（含 `level=2/3`），节点含 `id/name/parent_id/level/sort/status/product_count/created_at/updated_at`。
   - 增加可选查询参数 `?parent_id=<id>`：返回该父分类下的**直接子级**平铺列表（便于将来对每个层级做分步管理/分页），此时不带 `children`。
   - 每个节点的 `product_count`：改为「该分类自身 + 其全部子孙分类」直接挂载的商品数（与查询聚合口径一致）。实现：取子树 ids，`COUNT(*) where category_id IN (子树) AND deleted_at IS NULL`。
4. `CreateCategory`：
   - 解析可选 `parent_id`；调用 `validateParentLevel` 得 `level`（拒绝 >3）。
   - 写库时设置 `ParentID、Level`；无父则 `ParentID=nil, Level=1`。
   - 校验：同一父下名称不能重复（`name+parent_id` 唯一较验）。
5. `UpdateCategory`：
   - 支持更新 `parent_id`：若提供且变更，调用 `validateParentLevel` 校验新父（目标 `level≤3`），并同步更新本节点 `Level`；若该节点已有子级，需校验子级迁移后的最大深度仍 `≤3`（即本节点新 level + 其最大孙深度 ≤3），否则拒绝。
   - 鉴权保护：不允许把父级设置成自己的子孙（防止环）。
   - 前置校验旧父存在（若不改父则跳过）。
6. `DeleteCategory`：
   - 删除前 `countDirectChildren`>0 时拒绝："请先删除该分类的子分类"。
   - 叶子删除后：因 `products.category_id` 外键 `ON DELETE SET NULL`，商品自动置空（现状行为，不额外处理）。
7. `SortCategories`：保持按 id 更新 sort，不涉及层级（在同一层内排序由前端按 parent 分组后提交，本接口不区分层级）。

## 4. 假设与决策
- 三级语义：`level=1` 顶级（无父）、`level=2`（父为1级）、`level=3`（父为2级）；**不允许创建 level4**。
- 商品可挂**任意层级**（不强制叶子）。
- C端查询某分类时递归聚合其子孙分类商品（已确认）。
- C端不重构成三级导航，保持平铺布局（已确认）。
- 删除有子级的分类 → 拒绝；删除叶子 → 商品外键 `ON DELETE SET NULL` 置空（现状）。
- `category_type` 不参与三级层级约束，商品/服务分类同等对待。
- 存量分类全部置为 level1（迁移脚本），不自动构建历史父子关系。
