# 服务商商家审核页选项卡高亮修复计划

## Summary

目标：修复 `pages/sp/merchants/audit` 页面“全部”和“待审核”状态选项卡的高亮逻辑，避免点击一个选项卡时出现两个同时被选中的问题，同时保证筛选请求参数行为不变。

本次工作聚焦前端单页修复，不涉及后端接口、数据库或 PRD 文档调整。

## Current State Analysis

### 1. 现象定位

已确认问题页面为：

- `miniprogram/src/pages/sp/merchants/audit.vue`

当前页面顶部状态筛选栏通过以下逻辑高亮当前选项卡：

1. `statusTabs` 中每个标签有一个 `value`
2. `currentStatus` 默认值为 `0`
3. 模板使用 `:class="{ active: currentStatus === tab.value }"` 判断是否选中

### 2. 根因确认

已确认以下事实：

1. `audit.vue` 中“全部”标签的值为 `0`
2. `MerchantAuditStatus.PENDING` 在 `miniprogram/src/types/index.ts` 中也定义为 `0`
3. 因此以下两个标签当前共用了同一个值：
   - `全部`
   - `待审核`
4. 当 `currentStatus` 为 `0` 时，这两个标签都会命中 `active` 条件，导致同时高亮

结论：问题不是样式层的伪类冲突，而是前端筛选状态建模错误，“全部”与“待审核”没有使用不同的标识值。

### 3. 当前接口约束

已确认审核页调用的接口为：

- `getSpMerchantsPending()` -> `GET /api/v1/sp/merchants/pending`

当前请求参数逻辑为：

1. 默认仅传 `page`、`page_size`
2. 当 `currentStatus.value !== 0` 时，额外传 `status`
3. 这意味着当前实现把 `0` 同时用于：
   - “全部”的前端占位值
   - “待审核”的真实接口状态值

结论：修复时不仅要改选中态值，还要同步调整“何时传 `status`”的判断逻辑，否则会影响筛选结果。

## Proposed Changes

### 1. 修复 `audit.vue` 的筛选状态建模

文件：`/Users/yaotao/Documents/trae_projects/fz_yyc/miniprogram/src/pages/sp/merchants/audit.vue`

计划改动：

1. 为“全部”引入独立的前端筛选标识，不再使用数字 `0`
2. 推荐将“全部”改为字符串值，例如 `all`
3. 将 `currentStatus` 改为能同时容纳：
   - `all`
   - `MerchantAuditStatus.PENDING`
   - `MerchantAuditStatus.APPROVED`
   - `MerchantAuditStatus.REJECTED`
4. 保持模板高亮判断不变，但基于新值实现唯一选中

改动原因：

1. 这样能从数据层根除“全部”和“待审核”值冲突
2. 不需要依赖额外样式 hack 或复杂条件判断
3. 该方案语义最清晰，也便于后续新增筛选项

### 2. 调整接口请求参数拼装逻辑

文件：`/Users/yaotao/Documents/trae_projects/fz_yyc/miniprogram/src/pages/sp/merchants/audit.vue`

计划改动：

1. 仅当当前筛选项不是 `all` 时才传 `params.status`
2. 当选择“全部”时，不传 `status`
3. 当选择“待审核/已通过/已拒绝”时，传对应枚举值

改动原因：

1. 保持接口语义与当前后端实现一致
2. 避免因为改了前端选项卡值而把错误的字符串传给接口

### 3. 保持页面其他行为不变

文件：`/Users/yaotao/Documents/trae_projects/fz_yyc/miniprogram/src/pages/sp/merchants/audit.vue`

明确不改内容：

1. 搜索逻辑保持不变
2. 分页与加载更多逻辑保持不变
3. 商家卡片展示与跳转审核详情逻辑保持不变
4. 标签样式类名 `.tab-item.active` 保持不变

原因：

1. 当前问题明确集中在筛选值冲突
2. 采用最小改动可以降低回归风险

## Assumptions & Decisions

1. 本轮目标仅为修复选项卡高亮与筛选值冲突，不扩展到计数展示或交互重构
2. 决定使用“前端专用的 `all` 标识 + 接口状态枚举值”作为最终方案
3. 不修改 `MerchantAuditStatus` 枚举本身，因为后端状态 `0/1/2` 已是既定接口语义
4. 不修改 API 封装层 `getSpMerchantsPending()`，因为当前问题可以在页面层闭环解决
