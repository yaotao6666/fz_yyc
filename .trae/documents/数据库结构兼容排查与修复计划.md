# 数据库结构兼容排查、迁移重建与修复计划

## Summary

本次任务聚焦后端启动失败的数据库结构兼容问题，并按用户最新要求调整为“重建迁移体系”方案。目标是以一份新的、最新结构的单文件初始化 SQL 作为唯一迁移入口，替换旧迁移口径，重新生成初始化数据并执行迁移，使数据库结构与当前代码一致，恢复 `api` 容器正常启动。

本轮计划范围：

1. 排查当前数据库启动失败的根因，确认需要保留的最新表结构口径。
2. 删除旧迁移口径，重建单文件数据库初始化脚本。
3. 重新生成初始化数据，仅保留 `PRD.md` 中登记的服务商、商家账号及其必要关联测试数据。
4. 执行数据库迁移并重新验证后端容器启动。

本轮不包含：

1. 修改业务接口协议。
2. 保留旧的拆分迁移脚本口径。
3. 引入多文件迁移体系。

## Current State Analysis

### 1. 当前失败点已明确定位在 `merchant_staffs` 历史结构与当前代码不一致

- `server/pkg/database/mysql.go` 在 `InitDB()` 中会优先执行 `ensureMerchantStaffColumns(DB)`。
- 当前日志已明确报错：
  - `Unknown column 'openid' in 'merchant_staffs'`
  - 触发 SQL 为：`ALTER TABLE merchant_staffs ADD COLUMN wechat_bound_at ... AFTER openid`
- 这说明当前数据库不是按最新初始化脚本生成的，`merchant_staffs` 与当前代码要求的结构不一致。

### 2. 当前仓库的迁移入口实际已经收敛到单文件，但文档和数据口径仍有历史残留

- `server/migrations/` 目录当前实际只保留：
  - `20240101000000_full_init.sql`
  - `MIGRATION_GUIDE.md`
  - `REGRESSION_TEST_REPORT.md`
- `MIGRATION_GUIDE.md` 仍描述了已经不存在的旧拆分脚本：
  - `20240101000001_init.sql`
  - `20240101000002_seed_data.sql`
  - 以及其他旧迁移文件
- `测试账号文档.md` 里还保留了过时命令：
  - `go run cmd/main.go migrate up`
  - `20240101000002_seed_data.sql`

这说明当前问题不只是在运行时兼容补列，还包括迁移入口和初始化数据说明没有彻底统一。

### 3. 当前代码对 `merchant_staffs` 新字段已形成真实依赖

`server/pkg/database/mysql.go` 当前只补了以下字段：

1. `notify_enabled`
2. `browse_notify_enabled`
3. `wechat_bound_at`
4. `last_wechat_login_at`

但没有处理：

1. `openid`
2. `idx_merchant_staffs_openid`

以下后端逻辑已经直接依赖 `merchant_staffs.openid`：

- `server/internal/handlers/merchant/account.go`
  - 微信绑定时按 `openid` 查重
  - 微信解绑时清空 `openid`
  - 微信快捷登录时按 `openid` 查询员工
- `server/internal/models/models.go`
  - `MerchantStaff` 模型已声明 `OpenID`、`WechatBoundAt`、`BrowseNotifyEnabled`、`LastWechatLoginAt`
- `server/migrations/20240101000000_full_init.sql`
  - 新初始化库的 `merchant_staffs` 已包含 `openid` 与相关字段/索引

这说明 `openid` 不是可选优化字段，而是当前登录与绑定链路的必需字段。

因此，只修运行时补列虽然能缓解问题，但仍无法满足“删除旧迁移脚本、重新生成新的迁移数据、执行迁移”的最新要求。

### 4. 最新库结构应以当前模型和完整初始化脚本为准

- `server/migrations/20240101000000_full_init.sql` 里的 `merchant_staffs` 表已包含：
  - `openid`
  - `wechat_bound_at`
  - `notify_enabled`
  - `browse_notify_enabled`
  - `last_wechat_login_at`
  - `idx_merchant_staffs_openid`
- 因此本次问题不是完整初始化 SQL 缺失，而是历史库升级路径缺少兼容补丁。

### 5. 初始化账号口径已可直接从 `PRD.md` 和测试文档确认

- `PRD.md` 当前明确的开发环境测试账号：
  - 服务商管理员：`admin / admin123`
  - 商家员工：`merchant / merchant123`
- `测试账号文档.md` 中也与上述账号保持一致。
- 用户已明确：新初始化数据只需保留 `PRD.md` 中登记的服务商、商家账号即可。

## Proposed Changes

### 1. 删除旧迁移口径，重建单文件初始化脚本

#### 目标文件

- `server/migrations/20240101000000_full_init.sql`
- `server/migrations/MIGRATION_GUIDE.md`
- `server/migrations/REGRESSION_TEST_REPORT.md`
- `测试账号文档.md`
- `PRD.md`（仅在发现迁移账号或初始化说明与当前文档不一致时同步修正）

#### 修改内容

1. 在 `ensureMerchantStaffColumns()` 中先补 `openid`，再补 `wechat_bound_at`。
2. 重写 `20240101000000_full_init.sql`，确保它完整反映当前代码所需的最新表结构和初始化数据。
3. 清理文档中对旧拆分脚本、旧命令入口和不存在文件的引用。
4. 保持迁移体系为“单文件初始化脚本”这一唯一入口。

#### 原因

- 用户已明确选择“单文件重建”方案。
- 当前仓库实际也已经围绕 `full_init.sql` 运作，继续沿用单文件最符合现状。
- 文档和说明层仍有历史拆分脚本残留，需要一并清理，避免继续误导迁移方式。

### 2. 重新生成初始化数据，账号密码与 `PRD.md` 保持一致

#### 目标文件

- `server/migrations/20240101000000_full_init.sql`
- `测试账号文档.md`

#### 修改内容

1. 为 `openid` 增加独立的补列逻辑。
2. 初始化数据只保留当前需要的核心账号与必要演示数据：
   - 服务商管理员：`admin / admin123`
   - 商家员工：`merchant / merchant123`
3. 关联的服务商、商家、基础配送设置等数据需与账号可登录、可联调的最小闭环保持一致。
4. 若现有测试数据中存在与最新代码结构不匹配的部分，一并按当前结构重写。

#### 原因

- 用户已明确要求账号密码以 `PRD.md` 为准。
- 初始化数据应服务于当前登录、设置、员工、配送等核心链路，而不是保留历史冗余数据。

### 3. 在重建迁移脚本的同时修正 `merchant_staffs` 兼容逻辑

#### 目标文件

- `server/pkg/database/mysql.go`
- `server/internal/models/models.go`（只读对照，不计划修改，除非执行期发现与迁移定义不一致）

#### 修改内容

1. 在 `ensureMerchantStaffColumns()` 中先补 `openid`，再补 `wechat_bound_at`。
2. 增加 `idx_merchant_staffs_openid` 的兼容检查与补建逻辑。
3. 保持运行时兼容逻辑与新迁移脚本口径一致，避免老库和新库行为分叉。

#### 原因

- 即使采用新迁移脚本，当前环境里仍可能存在已运行的历史库。
- 运行时兼容逻辑仍然需要兜底，保证“旧库直接启动”和“重建迁移后启动”都能成功。

### 4. 执行数据库迁移

#### 目标文件

- `server/scripts/regression-test.sh`
- `server/scripts/regression.sh`
- `server/docker-compose.yml`

#### 修改内容

1. 统一迁移执行入口，避免继续引用不存在的 `cmd/main.go migrate up`。
2. 按当前仓库实际可执行方式落地迁移：
   - 直接导入新的 `20240101000000_full_init.sql`
   - 或通过现有回归脚本封装执行
3. 执行迁移前后验证数据库状态，确保新表结构和种子数据已经生效。

#### 原因

- 用户最新要求已经包含“执行迁移”，因此计划必须明确真实可用的迁移执行入口。
- 当前文档里的旧命令入口与仓库实际结构不一致，需要同步修正。

### 5. 重建镜像并验证容器恢复

#### 目标文件

- `server/docker-compose.yml`
- `server/Dockerfile`

#### 执行验证

1. 修改完成后重新构建并启动 `api`：
   - `docker compose up --build -d api`
2. 如迁移需要重建数据库内容，先执行新的初始化脚本，再启动 `api`。
2. 检查容器状态：
   - `docker compose ps`
3. 检查 `api` 启动日志：
   - `docker compose logs --tail 50 api`
4. 确认不再出现：
   - `Unknown column 'openid' in 'merchant_staffs'`
   - `初始化商家员工扩展字段失败`

## Assumptions & Decisions

### 已确认决策

1. 兼容修复以 `merchant_staffs` 为主，因为当前阻塞点已明确落在该表。
2. 新迁移体系采用单文件重建，不拆分为 schema/seed 多文件。
3. 新库结构以 `server/internal/models/models.go` 和当前实际代码使用字段为准。
4. 初始化账号只保留 `PRD.md` 中登记的服务商、商家账号。
5. 本轮既要修新迁移脚本，也要保留必要的历史库启动兼容能力。

### 本轮关键假设

1. 当前数据库中的 `merchant_staffs` 表已存在，只是缺失部分新字段。
2. 当前报错的首要根因是 `openid` 缺失；修复后仍需通过新迁移脚本统一结构，避免继续靠补列兜底。
3. `openid` 不需要唯一索引，沿用当前初始化 SQL 的普通索引口径即可。
4. 现有演示数据可以精简，但不能影响服务商登录、商家登录和基础联调。

## Verification Steps

### 1. 代码层验证

1. 新的 `20240101000000_full_init.sql` 能完整表达当前最新数据库结构。

4. 兼容逻辑同时覆盖字段和 `openid` 索引。
