# 数据库结构兼容重建与迁移收口计划

## Summary

- 目标：以 `server/migrations/20240101000000_full_init.sql` 作为唯一初始化入口，收敛数据库结构、初始化数据、回归脚本和文档口径，完成“删除旧迁移口径、重建迁移数据、执行迁移、账号与 `PRD.md` 保持一致”的收尾方案。
- 成功标准：
  1. 仓库内不再保留对旧拆分迁移脚本或不存在迁移命令的依赖说明。
  2. 初始化 SQL 与当前代码模型兼容，重点覆盖 `merchant_staffs.openid`、微信绑定字段、行为事件表等新增结构。
  3. 初始化账号仅保留 `admin / admin123` 与 `merchant / merchant123`，并与 `PRD.md`、迁移文档、测试账号文档一致。
  4. 回归脚本与实际登录路由一致，能基于新初始化数据完成基础验证。
  5. 执行迁移并重建 `api` 后，容器恢复健康，基础登录验证通过。

## Current State Analysis

### 已确认现状

- `server/migrations` 当前只剩 3 个文件：`20240101000000_full_init.sql`、`MIGRATION_GUIDE.md`、`REGRESSION_TEST_REPORT.md`，说明旧拆分 SQL 文件本体已不在仓库中。
- `server/migrations/20240101000000_full_init.sql` 已是单文件初始化脚本，包含：
  - 数据库创建与全量建表；
  - `merchant_staffs.openid`、`wechat_bound_at`、`browse_notify_enabled`、`last_wechat_login_at`；
  - `user_behavior_events` 表；
  - 最小初始化账号 `admin / admin123`、`merchant / merchant123`。
- `server/pkg/database/mysql.go` 已保留运行时兼容逻辑：
  - `ensureMerchantStaffColumns()` 先补 `openid` 再补其余字段；
  - `ensureMerchantStaffIndex()` 补 `idx_merchant_staffs_openid`；
  - `ensureUserBehaviorEventsTable()` 补行为事件表。
- `server/migrations/MIGRATION_GUIDE.md` 与 `测试账号文档.md` 已基本切到单文件初始化口径，且账号与 `PRD.md` 中的测试口径一致。

### 仍需收口的问题

- `server/scripts/regression-test.sh` 仍使用旧登录路由：
  - 服务商：`/api/v1/sp/auth/login`
  - 商家：`/api/v1/merchant/auth/login`
- `server/scripts/regression.sh` 同样保留旧服务商登录路由与旧展示口径。
- `server/migrations/REGRESSION_TEST_REPORT.md` 仍记录旧接口路径，已与当前后端真实路由不一致。
- `PRD.md` 仍有多处 `/api/v1/sp/auth/login` 旧描述，需要与当前实现重新核对并同步。
- `server/cmd/server/main.go` 当前真实公共登录路由为：
  - `/api/v1/auth/admin/login`
  - `/api/v1/auth/merchant/login`
  其中 `spGroup.POST("/auth/login", sp.Login)` 位于 JWT 保护组内，不适合作为初始登录入口，因此现有脚本/文档引用的旧路径会导致验证误判。

## Proposed Changes

### 1. 固化单文件迁移入口

- 文件：`server/migrations/20240101000000_full_init.sql`
- 处理：
  - 复核该文件与当前模型是否一致，不再恢复旧拆分迁移方式。
  - 维持“最新结构 + 最小初始化数据”的策略，不再回填历史演示商品、C 端用户、订单数据。
- 原因：
  - 用户已明确选择“单文件重建”；
  - 当前问题核心不是迁移工具链扩展，而是初始化结构和最小数据要稳定可复现。

### 2. 保留运行时兼容兜底

- 文件：`server/pkg/database/mysql.go`
- 处理：
  - 保留 `merchant_staffs` 的补列与补索引逻辑；
  - 保留 `user_behavior_events` 自动迁移逻辑；
  - 如执行时发现与最新 SQL 仍有字段/索引差异，仅做最小兼容补强，不改动业务逻辑。
- 原因：
  - 新库可直接用单文件初始化；
  - 历史库仍可能跳过重建，因此需要运行时兜底，避免再次因字段缺失导致 `api` 启动失败。

### 3. 清理迁移验证链路中的旧口径

- 文件：`server/scripts/regression-test.sh`
- 处理：
  - 将登录验证改为当前真实公共路由：
    - 服务商：`/api/v1/auth/admin/login`
    - 商家：`/api/v1/auth/merchant/login`
  - 保持初始化 SQL 调用单文件入口；
  - 校正脚本输出文案，只保留当前存在的测试账号与最小数据预期。
- 文件：`server/scripts/regression.sh`
- 处理：
  - 同步修正服务商登录路径；
  - 更新“测试账号”展示，不再误导为旧接口或旧演示数据。
- 文件：`server/migrations/REGRESSION_TEST_REPORT.md`
- 处理：
  - 将报告中的旧路径和旧结论替换为新路由与当前验证结果；
  - 明确报告基于单文件初始化 SQL。
- 原因：
  - 当前数据库结构虽然已更新，但脚本和报告仍会因为旧路径误判为失败，影响后续排查与交付。

### 4. 同步产品与使用文档

- 文件：`PRD.md`
- 处理：
  - 将服务商/商家登录接口描述与当前实现对齐；
  - 保留 `merchant / merchant123` 的测试口径；
  - 不新增本次范围外的产品能力描述。
- 文件：`server/migrations/MIGRATION_GUIDE.md`
- 处理：
  - 保持“单文件初始化入口”描述；
  - 如执行阶段发现示例命令或说明仍与脚本行为不一致，再一并修正。
- 文件：`测试账号文档.md`
- 处理：
  - 确认账号、初始化方式、数据范围与最终脚本一致；
  - 移除与当前初始化数据不符的示例描述。
- 原因：
  - 用户和工作区规则都要求代码、接口、初始化数据与 `PRD.md` 保持一致；
  - 迁移口径如果只改脚本不改文档，后续仍会反复出现误用。

### 5. 执行迁移与容器恢复验证

- 执行范围：
  - 停止或重建 `api` 容器，避免旧进程占用旧结构；
  - 使用 `server/migrations/20240101000000_full_init.sql` 重新导入数据库；
  - 重建并启动 `api`；
  - 查看容器健康状态与后端日志；
  - 使用初始化账号验证登录；
  - 运行 Go 测试与回归脚本做基础确认。
- 验证目标：
  - `merchant_staffs` 相关字段不再报缺失；
  - `api` 容器为 `healthy`；
  - `admin / admin123`、`merchant / merchant123` 可成功登录；
  - 回归脚本不再因旧路由失败。

## Assumptions & Decisions

- 决策：保留“单文件重建”而不是恢复多文件迁移体系。
- 决策：初始化账号仅保留 `admin / admin123` 与 `merchant / merchant123`。
- 决策：不在初始化 SQL 中恢复 C 端用户、商品、订单等历史演示数据。
- 决策：运行时兼容逻辑继续保留，作为历史库兜底，不替代单文件初始化。
- 假设：当前真实登录入口以 `server/cmd/server/main.go` 中 `/api/v1/auth/admin/login`、`/api/v1/auth/merchant/login` 为准；若执行阶段发现服务商侧另有正式公开入口，再以代码实际路由为准统一回写文档和脚本。
- 范围外：本轮不扩展新的业务表设计，不调整商家/服务商认证逻辑本身，只做迁移结构、初始化数据、脚本与文档口径修复。

## Verification Steps

1. 检查迁移目录，确认仅以 `server/migrations/20240101000000_full_init.sql` 为初始化入口。
2. 对照 `server/internal/models/models.go` 与 `server/pkg/database/mysql.go`，确认新增字段/索引/表均被 SQL 与运行时兼容逻辑覆盖。
3. 重新导入初始化 SQL，确认数据库创建成功。
4. 重建并启动 `api`，检查 `docker compose ps` 与 `docker compose logs --tail`，确认容器健康。
5. 用 `curl` 或脚本验证：
  - `POST /api/v1/auth/admin/login`
  - `POST /api/v1/auth/merchant/login`
6. 运行 `go test ./...`，确认后端基础编译与测试通过。
7. 运行修正后的 `server/scripts/regression-test.sh test` 或 `server/scripts/regression.sh`，确认回归脚本不再因旧路由误报。
