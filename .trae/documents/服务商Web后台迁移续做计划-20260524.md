# 服务商 Web 后台迁移续做计划

## Summary

- 目标：
  - 继续完成已启动但未收尾的“服务商从小程序迁移到 Web 后台”工作。
  - 保持后端 `server/` 与 `/api/v1/sp/*` 接口不变，仅调整前端承载端与系统文档口径。
  - 将当前系统的实际交付形态切换为“用户/C 端小程序 + 商家小程序 + 服务商 Web/PC 后台”，并在文档中说明后续可扩展为三角色 PC 后台管理模式。
- 当前阶段判断：
  - `web-admin/` 已完成初始化和首批页面落地，不再是“从 0 新建”的状态。
  - 当前真正阻塞项是 `web-admin/tsconfig.app.json` 的 TypeScript 6 配置报错，导致 `npm run build` 尚未通过。
  - 小程序服务商页面、登录态、接口封装、路由和文档口径仍大量保留，尚未进入“彻底下线”阶段。
- 本次计划的执行顺序：
  - 先修复 `web-admin` 构建与基础工程问题。
  - 再校准并补齐服务商 Web 页面与接口联调。
  - 然后删除小程序 `pages/sp/*` 及其依赖链路。
  - 最后统一 README、PRD、测试文档与验收结果。

- 变更文件：

    - `web-admin/src/style.css`
    - `web-admin/src/components/HelloWorld.vue`
    - `web-admin/src/assets/*`
- 做法：
  - 以“移除废弃配置”为主修复方案，优先删除 `tsconfig.app.json` 中的 `baseUrl`，仅保留路径别名映射所需的最小配置。
  - 若 `vue-tsc` 仍提示路径解析问题，则同步将 `paths` 映射改为显式相对路径，并保证与 `vite.config.ts` 中的 `@ -> src` 别名一致。
  - 清理未被业务入口使用的 Vite 模板残留文件，避免后续诊断中出现无意义噪音。

  - `web-admin` 必须先达到可安装、可构建、可运行的最低交付标准，后续迁移才有承接对象。

## Assumptions & Decisions

- 决策 1：本次继续沿用已落地的 `web-admin/` 目录，不重新新建第二个后台工程。
- 决策 2：Web 技术栈保持 `Vite + Vue3 + TypeScript + Pinia + Vue Router + Element Plus`，不再切换框架。
- 决策 3：本次不修改任何后端接口、数据模型和数据库结构，只迁移前端承载端。
- 决策 4：当前真正实施到 PC 的只有“服务商后台”。
  - 文档中会改成“三角色 PC 后台管理的演进模式”。
  - 但本轮不会新增商家 PC 后台和用户 PC 后台项目。
- 决策 5：小程序中的服务商入口采用“直接删除入口和页面”的方式，不保留迁移提示页。
- 决策 6：小程序清理必须放在 `web-admin` 构建可用之后执行，避免交付中断。
- 假设 1：现有 `/api/v1/sp/*` 接口字段足以支撑本轮 Web 页面迁移，不需要追加后端字段。
- 假设 2：商家端与 C 端不依赖 `miniprogram/src/stores/sp.ts` 和 `pages/sp/*` 页面存在。
- 假设 3：当前多品牌构建方案仅作用于小程序，与 `web-admin` 独立，不需要本轮为 Web 再做多品牌切换。
