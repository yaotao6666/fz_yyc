# 商家员工 UnionID 绑定改造计划

## Summary

- 目标：为商家员工补齐 `unionid` 绑定与持久化能力，给后续服务号侧身份打通预留数据基础。
- 本轮范围按用户最新决定收敛为：
  - 员工表新增 `unionid` 字段。
  - 商家微信绑定/快捷登录链路补齐 `unionid` 获取与落库。
- 明确不做：
  - 不新增服务号订阅映射表。
  - 不新增服务号订单通知发送能力。
  - 不改“声音提醒管理/推送管理”页面、文案和开关。
- 结果要求：
  - 员工表新增 `unionid` 字段，数据库初始化脚本与运行时兼容补列同步更新。
  - 绑定微信或快捷登录时，后端能从微信 `code2session` 获取 `unionid` 并写入员工记录。

## Current State Analysis

### 现有员工与提醒设置

- 员工模型位于 `server/internal/models/models.go`，`MerchantStaff` 目前只有：
  - `openid`
  - `wechat_bound_at`
  - `notify_enabled`
  - `browse_notify_enabled`
  - `last_wechat_login_at`
- 商家设置接口位于 `server/internal/handlers/merchant/handler.go`：
  - `GetSettings()` 返回当前登录员工的 `notify_enabled`、`browse_notify_enabled`。
  - `UpdateSettings()` 仅支持更新这两个员工级提醒开关。
- 员工管理接口位于 `server/internal/handlers/merchant/staff.go`：
  - `GetStaffList()` 直接返回 `MerchantStaff`
  - `UpdateStaff()` 仅支持更新角色、状态、下单提醒、浏览提醒，不支持服务号推送字段。

### 现有微信绑定与快捷登录

- 商家员工微信绑定/快捷登录位于 `server/internal/handlers/merchant/account.go`。
- 目前已存在：
  - `BindWechat()`
  - `WechatQuickLogin()`
- 当前链路基于小程序 `code -> openid`，尚无：
  - `unionid` 存储

### 数据与初始化现状

- 数据库初始化入口是 `server/migrations/20240101000000_full_init.sql`。
- 运行时数据库兼容逻辑位于 `server/pkg/database/mysql.go`，当前已负责给 `merchant_staffs` 补：
  - `openid`
  - `wechat_bound_at`
  - `browse_notify_enabled`
  - `last_wechat_login_at`
- 当前没有：
  - `merchant_staffs.unionid`

## Proposed Changes

### 1. 员工模型与数据库结构补齐

#### 文件

- `server/internal/models/models.go`
- `server/migrations/20240101000000_full_init.sql`
- `server/pkg/database/mysql.go`

#### 变更

- 在 `MerchantStaff` 中新增：
  - `UnionID string`，用于后续与服务号侧身份打通。
- 在初始化 SQL 中：
  - 补员工表 `unionid` 字段
- 在 `mysql.go` 中：
  - 追加 `merchant_staffs.unionid`

#### 原因

- 用户已明确要求本轮只绑定 `unionid`，因此只补齐员工主表字段与兼容迁移，不扩展额外数据结构。

### 2. 商家微信绑定链路补齐 unionid

#### 文件

- `server/internal/handlers/merchant/account.go`

#### 变更

- 扩展当前小程序 `code2session` 解析结果，除 `openid` 外同时读取 `unionid`。
- `BindWechat()` 绑定时：
  - 将员工表 `openid`、`unionid`、`wechat_bound_at` 一并更新。
- `WechatQuickLogin()` 维持按小程序 `openid` 登录，不改登录口径；但登录成功后应同步回写最新 `unionid`。

#### 原因

- 员工后续要与服务号侧身份打通，当前最小可行基础就是先稳定保存 `unionid`。

### 3. 员工信息返回结构同步 unionid

#### 文件

- `server/internal/handlers/merchant/staff.go`
- `server/internal/handlers/merchant/handler.go`
- `miniprogram/src/types/index.ts`

#### 变更

- 员工列表、当前登录员工设置返回中增加 `unionid` 字段。
- `MerchantStaff`、`MerchantSettings` 相关类型同步补齐 `unionid` 字段，便于前端后续展示或调试。

#### 原因

- 既然本轮只做 `unionid` 绑定，那么返回结构也应把该字段透出，避免后续排查时仍需查数据库。

## Assumptions & Decisions

- 已决策：本轮只补齐员工 `unionid` 绑定，不扩展服务号推送闭环。
- 已决策：不新增服务号相关页面开关，不修改现有提醒/推送管理能力。
- 假设：当前小程序 `code2session` 响应可返回 `unionid`，且已在同一微信开放平台下配置完成。
- 决策：现有 `openid` 登录口径保持不变，`unionid` 只作为附加身份字段落库。

## Verification

### 后端

- 执行 `go test ./...`，确保新增模型、回调处理、支付成功通知链路不报编译错误。
- 重建 `api` 容器并检查服务健康。
- 验证数据库：
  - `merchant_staffs` 新增 `unionid`
- 验证接口：
  - 绑定微信后员工表可写入 `unionid`
  - 微信快捷登录成功后员工表可同步回写 `unionid`
  - `GET /api/v1/merchant/settings` 与 `GET /api/v1/merchant/staff` 能返回 `unionid`

### 前端

- 执行 `npm run build:mp-weixin`。
- 商家端验证：
  - 微信绑定成功后前端状态回显不回归
  - 员工列表或登录态若消费 `unionid` 字段，不出现类型错误

### 联调场景

- 场景 1：员工绑定微信成功后，数据库中 `openid`、`unionid` 同时存在。
- 场景 2：员工快捷登录成功后，如历史记录缺少 `unionid`，可自动补齐。
- 场景 3：没有 `unionid` 返回时，不影响现有 `openid` 登录与绑定流程。
