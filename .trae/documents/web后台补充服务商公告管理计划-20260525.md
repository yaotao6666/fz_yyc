# Web 后台补充服务商公告管理计划

## Summary

- 目标：
  - 在现有 `web-admin/` 服务商 Web 后台中补上“系统公告管理”能力。
  - 复用已保留的后端 `/api/v1/sp/announcements*` 接口，不新增后端接口、不调整数据模型。
  - 对齐此前从小程序下线的服务商公告页面范围，让服务商可以在 PC 后台完成公告列表查看、创建、编辑和删除（后端实际为置 `status=0`）。
- 本次补充的能力边界：
  - 服务商公告列表页
  - 服务商公告新增/编辑页
  - 后台菜单入口与路由
  - Web 端 API 封装与类型
  - 文档同步为“已由 Web 后台承接”
- 不在本次范围内：
  - 不新增后端接口
  - 不修改 `server/internal/handlers/sp/announcement.go` 的接口语义
  - 不恢复小程序端公告页面

## Current State Analysis

### 1. 后端公告接口已经完整保留

- 已确认接口注册仍存在于：
  - `server/cmd/server/main.go`
- 当前可复用的接口为：
  - `GET /api/v1/sp/announcements`
  - `GET /api/v1/sp/announcements/:id`
  - `POST /api/v1/sp/announcements`
  - `PUT /api/v1/sp/announcements/:id`
  - `DELETE /api/v1/sp/announcements/:id`
- 实现文件：
  - `server/internal/handlers/sp/announcement.go`
- 当前请求/响应字段已明确：
  - 列表：返回 `list + pagination`
  - 详情：返回单条 `Announcement`
  - 创建/更新请求体：
    - `title`
    - `content`
    - `status`（`0` 或 `1`）
  - 删除行为：
    - 实际是将 `status` 更新为 `0`

### 2. 公告模型字段非常简单，适合直接接到后台表单

- 模型定义位于：
  - `server/internal/models/models.go`
- 当前公告表字段：
  - `id`
  - `service_provider_id`
  - `title`
  - `content`
  - `status`
  - `created_at`
  - `updated_at`
- 结论：
  - `web-admin` 页面不需要复杂 schema 适配，表格和表单都可以直接围绕这几个字段展开。

### 3. `web-admin` 当前尚未接入任何公告 API、路由或菜单

- 当前 API 文件：
  - `web-admin/src/api/sp.ts`
  - 只包含登录、商家、分账、数据分析、设置、上传等接口，没有公告封装。
- 当前类型文件：
  - `web-admin/src/types/sp.ts`
  - 没有 `Announcement` 相关类型定义。
- 当前路由文件：
  - `web-admin/src/router/index.ts`
  - 没有公告管理路由。
- 当前布局菜单：
  - `web-admin/src/layouts/AppLayout.vue`
  - 只包含：
    - 工作台
    - 商家列表
    - 分账历史
    - 数据分析
    - 服务商设置
- 当前页面目录：
  - `web-admin/src/views/`
  - 也不存在 `announcement/` 相关页面文件。

### 4. 产品和规格文档已经明确“公告管理应该由 Web 后台承接”

- 历史下线 spec：
  - `.trae/specs/remove-sp-announcement-pages/spec.md`
- 其中已明确：
  - 小程序端移除服务商公告页面
  - 后端接口保留，供后续 PC 端复用
- 当前 PRD 口径：
  - `docs/prd/PRD-接口文档.md`
  - `docs/prd/PRD-功能说明.md`
  - `docs/prd/完整业务链路目录.md`
- 已明确存在“发布系统公告”这条服务商业务链路，但 `web-admin` 代码尚未落地，存在产品文档与前端交付不一致。

## Proposed Changes

### 1. 为 `web-admin` 增加公告管理类型与接口封装

- 变更文件：
  - `web-admin/src/types/sp.ts`
  - `web-admin/src/api/sp.ts`
- 计划内容：
  - 在 `types/sp.ts` 中新增公告相关类型：
    - `AnnouncementItem`
    - `AnnouncementListResponse`
    - `AnnouncementFormData`
  - 在 `api/sp.ts` 中新增公告相关方法：
    - `getAnnouncements`
    - `getAnnouncementDetail`
    - `createAnnouncement`
    - `updateAnnouncement`
    - `deleteAnnouncement`
- 设计约束：
  - 保持与现有 `unwrapApiResponse` 统一风格一致
  - 不创建新的请求层，继续复用 `/api/v1/sp/announcements*`

### 2. 为后台增加公告管理路由

- 变更文件：
  - `web-admin/src/router/index.ts`
- 计划内容：
  - 增加公告列表页路由：
    - `/announcements`
  - 增加公告新增页路由：
    - `/announcements/new`
  - 增加公告编辑页路由：
    - `/announcements/:id/edit`
- 路由 meta 标题需要与现有后台风格一致，例如：
  - `公告管理`
  - `新增公告`
  - `编辑公告`
- 路由全部继续挂在当前受保护布局下，要求登录后可访问。

### 3. 在左侧菜单加入“公告管理”入口

- 变更文件：
  - `web-admin/src/layouts/AppLayout.vue`
- 计划内容：
  - 在现有 `menuItems` 中加入公告管理入口
  - `activeMenu` 的激活规则需要兼容：
    - `/announcements`
    - `/announcements/new`
    - `/announcements/:id/edit`
- 原因：
  - 这是服务商端完整业务链路中的一项核心管理能力，应该作为一级菜单与商家列表、分账历史同级呈现。

### 4. 新增公告列表页，覆盖“查看 + 新建入口 + 编辑入口 + 删除”

- 新增文件：
  - `web-admin/src/views/announcement/AnnouncementListView.vue`
- 页面职责：
  - 调用 `GET /api/v1/sp/announcements`
  - 展示公告列表
  - 展示分页
  - 提供“新增公告”按钮
  - 提供“编辑”与“删除”操作
- 列表建议字段：
  - 标题
  - 状态
  - 创建时间
  - 更新时间
  - 操作列
- 删除设计说明：
  - 前端调用 `DELETE /api/v1/sp/announcements/:id`
  - 文案上呈现为“删除公告”
  - 但需在计划中明确：后端当前是逻辑删除/禁用（`status=0`），不是物理删除
- 状态展示建议：
  - `1` 显示为“已发布”
  - `0` 显示为“草稿/已停用”

### 5. 新增公告表单页，覆盖“新增 + 编辑”双模式

  - 编辑模式调用 `GET /api/v1/sp/announcements/:id`
  - 新增模式调用 `POST /api/v1/sp/announcements`
  - 编辑模式调用 `PUT /api/v1/sp/announcements/:id`

  - 提交成功后回到列表或停留当前页并给出成功提示，执行时以现有 `web-admin` 页面交互风格为准
- 状态控件建议：
  - 使用现有 Element Plus 表单控件
  - 页面层显示语义为“草稿 / 发布”

## Assumptions & Decisions

- 决策 1：本次采用“列表页 + 单表单页（新增/编辑共用）”的两页结构，而不是拆成列表/详情/编辑三页。
- 决策 2：菜单层级保持当前后台简洁风格，公告管理作为一级菜单加入，不新增二级菜单。
- 决策 3：删除操作前端文案按“删除公告”呈现，但实现仍遵循后端当前接口语义，即把 `status` 更新为 `0`。
- 决策 4：状态值继续直接对齐后端：
  - `1` = 已发布
  - `0` = 草稿/禁用
- 决策 5：本次不新增筛选接口，因此列表页默认只做分页与基础展示，是否加入前端本地状态筛选在执行时以低成本实现为准，但不依赖后端新增参数。
- 假设 1：当前服务商账号已有权限访问 `/api/v1/sp/announcements*`
- 假设 2：现有 `Announcement` 数据量不大，当前分页结构足以支撑后台使用
- 假设 3：接口返回使用当前统一响应格式，适配 `unwrapApiResponse`
