# 单商家架构调整与小程序升级计划

## 一、总结

基于现有架构，将系统从"服务商管理多商家"模式调整为"单商家模式"，并重新定义三端职责：

1. **客户端小程序**（现有，清理升级）：仅面向 C 端用户下单，移除全部商家管理能力。
2. **服务人员接单小程序**（新增，PRD 定义）：独立身份，用于服务人员注册审核、登录、查看与接单。
3. **商户 PC 后台**（web-admin 改造，PRD 定义）：作为单商户的统一管理后台，承接商品/分类/订单/核销/服务人员/公告等管理。

**交付范围**：PRD 文档全量更新（`PRD.md` + `docs/prd/*` 四份）+ 小程序商家管理残留清理校验。不含后端代码改造、不含服务人员小程序代码实现。

**关键约束**：PRD 只记录"是什么"，不出现变更原因、决策过程或"由 X 改为 Y"的备注，保证文档处于最新可读状态。

## 三、目标架构定义（PRD 基线）

### 3.1 角色

| 角色 | 入口 | 职责 |
| --- | --- | --- |
| C 端用户 | 客户端小程序（扫码） | 浏览、加购、下单支付、查看订单、申请退款 |
| 服务人员 | 服务人员接单小程序（独立） | 注册申请/登录、查看待接订单、接单、查看已接订单与历史；不核销 |
| 商户管理员 | 商户 PC 后台（web-admin） | 商品/分类/订单/核销/满减/打印机/公告/服务人员管理/数据分析/设置 |

### 3.2 单商家模式
- 系统只有一个商户（单条 `merchants` 记录）。
- 移除服务商实体、`service_provider_id` 字段、多商家管理能力。
- 微信支付服务商凭证（`mch_id`/`api_key`/`api_v3_key`/证书）下沉为系统级配置，不作为可管理实体。

### 3.3 接单与核销分离
- **接单**：服务人员在小程序端对待接订单执行接单，订单记录接单人 `accepted_by_staff_id` + `accepted_at`。
- **核销**：由商户管理员在 PC 后台执行订单核销（含扫码核销与订单详情核销），核销人 `completed_by_name`。
- 接单与核销是两个独立动作，接单人 ≠ 核销人。

### 3.4 服务人员身份
- 独立于 `merchant_staffs`，新增 `service_staffs` 表。
- 管理方式：PC 后台直接添加 + 小程序端注册申请（需 PC 后台审核通过后生效）。
- 登录：账号密码或微信快捷登录。
