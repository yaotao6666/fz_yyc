# 商家设置页订单提示音开关保存接口修复计划

## Summary

目标：修复商家端 `pages/merchant/settings` 页面中“订单提示音”开关只改本地状态、不调用后端保存接口的问题，使该开关能够在当前登录员工维度持久化保存，并在重新进入页面、重新登录后正确回显。

本次修复采用最小影响方案：复用现有数据库字段 `merchant_staffs.notify_enabled`，扩展现有商家设置接口 `/api/v1/merchant/settings` 的读写能力，并让前端页面与 `auth` store 统一走接口同步，不新增独立接口。

## Current State Analysis

### 1. 前端页面当前只保存本地缓存，没有调用保存接口

已确认：

1. `miniprogram/src/pages/merchant/settings.vue`

   * 页面上“订单提示音”使用 `soundEnabled = computed(() => authStore.soundEnabled)` 展示。

   * `switch` 的 `@change` 只执行 `handleSoundToggle()`。

   * `handleSoundToggle()` 当前仅调用 `authStore.setSoundEnabled(!!e.detail.value)`。
2. `miniprogram/src/stores/auth.ts`

   * `setSoundEnabled()` 只更新 `state.soundEnabled` 并写入本地缓存 `merchant_sound_enabled`。

   * 没有任何接口请求。

结论：当前“订单提示音”开关只是本地开关，不是服务端持久化设置，所以刷新、换端、重新登录后可能与真实员工设置不一致。

### 2. 后端现有商家设置接口未覆盖提示音字段

已确认：

1. `server/internal/handlers/merchant/handler.go`

   * `GetSettings()` 当前只返回：

     * `announcement`

     * `business_hours`

     * `min_order_amount`

     * `takeout_enabled`

     * `dine_in_enabled`

     * `delivery_settings`

   * `UpdateSettingsRequest` 当前只接收：

     * `takeout_enabled`

     * `dine_in_enabled`

   * `UpdateSettings()` 当前也只更新商家表上的这两个字段。

结论：即便前端愿意调 `/api/v1/merchant/settings`，后端当前也没有 `notify_enabled` 的读写能力。

### 3. 数据库里已经存在可复用字段

已确认：

1. `server/internal/models/models.go`

   * `MerchantStaff.NotifyEnabled bool` 已存在，字段名为 `notify_enabled`。
2. `server/internal/handlers/merchant/staff.go`

   * 员工更新接口已经支持 `NotifyEnabled *bool`，说明该字段在业务上是有效字段，不是废弃设计。

结论：订单提示音开关天然更适合落在“当前员工”的通知偏好，而不是商家全局配置；本次修复可以直接复用该字段，不需要新表或新字段。

### 4. 前端类型也还未声明该字段

已确认：

1. `miniprogram/src/types/index.ts`

   * `MerchantSettings` 当前没有 `notify_enabled` 字段。
2. `miniprogram/src/api/index.ts`

   * `getMerchantSettings()` / `updateMerchantSettings()` 已存在，但类型未覆盖提示音字段。

结论：除了接口实现，还需要补齐前端类型和页面读写逻辑，才能形成完整链路。

## Proposed Changes

### 1. 扩展商家设置接口，返回当前员工的提示音开关

#### 文件：`server/internal/handlers/merchant/handler.go`

变更内容：

* 在 `GetSettings()` 中增加当前登录员工查询。

* 从当前员工记录返回 `notify_enabled`。

* 若员工记录不存在，则按默认值 `true` 返回，保持现有体验。

原因：

* 设置页首次展示必须以服务端持久化值为准，不能继续只依赖本地缓存。

实施方式：

* 通过当前 JWT 取到的 `merchantID` 和登录态中的用户名/员工信息定位当前员工记录。

* 若现有中间件上下文可直接取得员工标识，则直接复用；否则沿用当前 token 信息中可得字段查询员工。

### 2. 扩展商家设置更新接口，支持保存 `notify_enabled`

#### 文件：`server/internal/handlers/merchant/handler.go`

变更内容：

* 在 `UpdateSettingsRequest` 中新增 `NotifyEnabled *bool`。

* `UpdateSettings()` 继续处理原有 `takeout_enabled` / `dine_in_enabled`。

* 当 `notify_enabled` 有值时，同时更新当前员工的 `merchant_staffs.notify_enabled`。

原因：

* 页面开关应走现有 `/api/v1/merchant/settings` 保存，不额外新增接口，符合最小改动原则。

实施方式：

* 对 `models.Merchant` 与 `models.MerchantStaff` 分开更新。

* `notify_enabled` 使用指针类型，避免未传时误覆盖。

* 更新员工记录失败时返回错误，避免页面误认为保存成功。

### 3. 补齐前端商家设置类型与 API 调用

#### 文件：`miniprogram/src/types/index.ts`

变更内容：

* 在 `MerchantSettings` 中新增：

  * `notify_enabled?: boolean`

原因：

* 页面和 API 调用需要明确类型约束，避免运行时弱类型读写。

#### 文件：`miniprogram/src/api/index.ts`

变更内容：

* 保持 `getMerchantSettings()` 不变，复用扩展后的返回结构。

* `updateMerchantSettings()` 接受 `notify_enabled` 字段。

原因：

* 与现有设置页请求方式保持一致，不新增前端接口封装复杂度。

### 4. 修复设置页开关初始化与保存逻辑

#### 文件：`miniprogram/src/pages/merchant/settings.vue`

变更内容：

* `onShow()` 加载设置时，不只读配送状态，同时读取 `notify_enabled` 并同步到 `authStore`。

* `handleSoundToggle()` 改为异步：

  * 先根据用户操作得到目标值

  * 调用 `updateMerchantSettings({ notify_enabled: value })`

  * 成功后再更新 `authStore.setSoundEnabled(value)`

  * 失败时回滚 UI，并提示“保存失败”

* 增加开关保存中的防抖/锁，避免用户连续快速切换造成状态错乱。

原因：

* 开关应该以接口成功为准更新本地状态。

* 页面重新进入后应显示服务端真实状态，而不是旧缓存。

实施方式：

* 增加 `soundSaving` 状态控制。

* `switch` 建议绑定 `:disabled="soundSaving"`，防止重复提交。

### 5. 统一 `auth` store 的本地状态与服务端状态来源

#### 文件：`miniprogram/src/stores/auth.ts`

变更内容：

* 保留 `soundEnabled` 本地状态与 `merchant_sound_enabled` 缓存，作为页面即时反馈与离线兜底。

* 但明确以 `getMerchantSettings().notify_enabled` 为登录后/页面展示时的最终来源。

* `setSoundEnabled()` 继续只负责更新本地状态，不直接发请求。

原因：

* 将“状态更新”和“接口保存”职责分离，避免 store 行为过重。

* 保持与现有页面结构兼容。

## Assumptions & Decisions

### 已锁定决策

1. 提示音开关保存维度采用“当前商家员工”而不是“商家全局”。
2. 复用现有 `/api/v1/merchant/settings` 接口，不新增独立的 `notify-enabled` 接口。
3. 前端以服务端返回的 `notify_enabled` 为准，本地缓存只作兜底。
4. 保存失败时不乐观提交，必须回滚为接口保存前的值并提示失败。

### 实施假设

1. 当前登录 token 中已有足够信息定位员工记录；若实现时发现无法稳定定位，则需要在中间件上下文中补充 staff 标识后再继续。
2. 现有 `merchant_staffs.notify_enabled` 字段即为订单提示音开关的正确持久化字段。

## Verification Steps

执行修复后，按以下顺序验证：

1. 设置页初始化验证

   * 商家登录后进入 `pages/merchant/settings`

   * 确认“订单提示音”显示值与后端 `notify_enabled` 一致

2. 保存接口验证

   * 将“订单提示音”从开启切换为关闭

   * 确认触发 `/api/v1/merchant/settings` 更新请求

   * 确认请求体包含 `notify_enabled`

   * 确认后端员工表对应字段被更新

3. 页面回显验证

   * 切换成功后退出设置页再进入

   * 确认开关状态仍保持

4. 登录态回归验证

   * 退出登录后重新登录

   * 确认开关状态仍为上次保存值

5. 失败回滚验证

   * 模拟接口失败

   * 确认页面开关回滚到原值

   * 确认提示“保存失败”或等价信息

6. 功能联动验证

   * 开启时收到 `order_notify` 推送应播放提示音

   * 关闭时收到 `order_notify` 推送仍可收到 toast / 推送，但不播放提示音
